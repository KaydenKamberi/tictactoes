GitHub Link: View Code for CP02

What I built: I implemented a full user authentication system. This includes backend Express routes for registration, login, and logout, and a frontend that communicates with these routes using the Fetch API. User data is persisted in a local JSON file.

What was hard: The most difficult part was managing the file structure. I accidentally created duplicate folders and files, which made the server and .gitignore act unpredictably until I flattened the tree back to the root.

What I'd do differently: I would stick strictly to the required file structure from the very beginning to avoid having to move files and fix broken paths later.

A/B testing note: I tried hiding only the 3x3 board div, but switched to hiding the entire game section so the "Game" header wouldn't stay visible to logged-out users.

CP03-game

The tag: CP03-game

GitHub Link: View code for CP03-game

What I built: I built the interactive game board UI. I used a JavaScript loop to dynamically generate a 3x3 grid of cells and attach click listeners to each one. The app now tracks an internal array of the board state, prevents players from overwriting existing moves, and updates a turn indicator to swap between Player X and Player O.

What was hard: Figuring out how to connect a physical click on the screen to a specific slot in my JavaScript array was tricky. I ended up using HTML data attributes (dataset.index) to pass the exact cell number to the click handler.

What I'd do differently: Right now, the X and O are just standard text. In the future, I'd like to add specific CSS classes to the cells when they are clicked so I can give X and O different colors to make the board pop more.

AI usage note: I used AI to help structure the handleCellClick function and the logic for swapping players, but I had to manually integrate it into my existing DOMContentLoaded setup so it wouldn't break my login hiding/showing logic.

A/B testing note: I debated hardcoding the 9 individual div cells directly into the HTML file, but I chose to generate them dynamically in main.js instead. This kept my HTML cleaner and allowed me to attach the event listeners inside the exact same loop that created them.

CP04-pvp

The tag: CP04-pvp

GitHub Link: Add your CP04 commit link here

What I built: I implemented the core rules of Tic Tac Toe. The app now checks for a win or a draw after every single move using a predefined array of the 8 possible winning combinations. I also added a scoreboard to track wins for Player X and Player O, along with a "Play Again" button that resets the board state without reloading the page.

What was hard: Figuring out the exact timing for the win detection was tricky. I initially realized that if I checked for a win *after* switching the `currentPlayer` variable, the game would announce that the wrong person won. I had to carefully order my code so the state updates, the win is checked, and *then* the turn swaps.

What I'd do differently: Right now, the game just stops when someone wins and shows text. Next time, I'd like to add a visual highlight (like changing the background color of the three winning cells) so it's instantly obvious where the winning line is.

AI usage note: I used AI to help write the `checkWinOrDraw` loop and map out the 2D array of winning index combinations. However, I made sure to customize how it affected my UI, specifically integrating the score counters and the hidden reset button.

A/B testing note: For the "Play Again" feature, I debated whether to just use `window.location.reload()` to refresh the page entirely. I chose to write a custom `resetBoard()` function instead, because reloading the page would have wiped out the `scoreX` and `scoreO` variables we were tracking in memory.

CP05-history

The tag: CP05-history

GitHub Link: View Code for CP05

What I built: I implemented game history persistence by saving each game's result (winner, players, and timestamp) to a games.json file. The backend now includes a /save-game endpoint to store game data and a /games endpoint to retrieve the history. The frontend sends game results to the backend whenever a game ends.

What was hard: The most challenging part was debugging why the game data wasn't saving to games.json. I initially thought the issue was in the server-side logic, but it turned out to be a client-side problem where the playerX value was empty due to session management. I fixed it by ensuring the user was properly logged in and the session was maintained.

What I'd do differently: I would have added more detailed error logging on both the client and server sides earlier. This would have helped me pinpoint the issue faster instead of assuming it was a backend problem.

AI usage note: I used AI to help review my code and identify potential issues, but ultimately, I diagnosed and fixed the problem myself by testing the endpoints manually and checking the browser's Network tab.

A/B testing note: I considered storing the game history in memory (e.g., a JavaScript array) but chose to use a JSON file for persistence. This ensures the data remains available even after the server restarts.

CP06-ai

The tag: CP06-ai

GitHub Link: View Code for CP06

What I built: I added a PvAI (Player vs. AI) mode to the game, allowing players to choose between PvP and PvAI using a dropdown selector. The AI uses the Groq API to generate its moves dynamically. I implemented a backend proxy endpoint (/get-ai-move) to securely call the Groq API from the server, avoiding exposure of the API key in the frontend. The AI responds with optimal moves, and the game updates the UI to reflect the AI's turn.

What was hard: The most challenging part was ensuring the Groq API key was securely handled. Initially, I tried calling the API directly from the frontend, but realized that process.env doesn't work in browser JavaScript. I had to refactor the code to use a backend proxy, which required setting up a new endpoint and updating the frontend to call it.

What I'd do differently: I would have planned the backend-frontend communication earlier to avoid the initial confusion about where to place the API key. Additionally, I would have added more detailed error handling for the Groq API calls to make debugging easier.

AI usage note: I used AI to help structure the backend proxy endpoint and the frontend logic for handling AI moves. However, I had to manually ensure the API key was securely stored and accessed only on the server side.

A/B testing note: I considered using a client-side AI library for simplicity, but chose the Groq API for its flexibility and power. This required a backend proxy, but it ensured the API key remained secure and the AI could be easily upgraded or replaced in the future.
